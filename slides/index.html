教學簡報｜給用過 ChatGPT、但沒聽過 RAG 的人

RAG 是什麼？
讓 AI 先查資料再回答

內容整理自 5 篇資料建成的 LLM Wiki：1 篇奠基論文、1 篇切塊指南、1 篇 Anthropic 工程文章、1 篇失敗案例論文、1 篇 RAG 與微調比較。

學習目標：說出 RAG 解決什麼問題 → 畫出流程 → 理解切塊與檢索 → 分辨 RAG 與微調 → 認得常見失敗點。

為什麼需要 RAG？

語言模型把知識存在自己的參數裡，這有三個麻煩（Lewis 等人，2020）：

  • 難以擴充或修改它的記憶
  • 難以說明答案是怎麼來的
  • 可能產生幻覺（hallucination）：講得像真的，其實是錯的

另外，通用模型不一定懂你的領域，也有知識截止日（Barnett 等人，2024）。

RAG 的想法：別全靠模型記憶，回答前先去外部資料查。

閉書考 vs 開書考

只靠模型參數作答叫 closed-book；回答時能查資料叫 open-book。論文在 Natural Questions 上的 Exact Match 分數：

T5-large（770M，閉書）28.9
T5-11B（閉書）34.5
DPR（開書）41.5
RAG-Sequence（開書）44.5

RAG 的可訓練參數約 626M，比 T5-11B 小很多，卻分數更高。

論文裡的 RAG：兩種記憶

問題 x查詢編碼器變成向量
→
檢索器（DPR）在索引中找 top-K 份文件
→
生成器（BART-large）把問題與文件串接後生成答案
  • 參數記憶：BART-large 模型本身（約 400M 參數）
  • 非參數記憶：2018 年 12 月的 Wikipedia，切成 100 字一塊，共 2,100 萬份，用 FAISS 建索引

記憶是原始文字，所以人讀得懂、也寫得動：改索引，就能改變模型能用的知識。

RAG-Sequence 與 RAG-Token

RAG-Sequence整段答案都用同一份文件
RAG-Token每個字可以參考不同文件

論文的例子：輸入「Hemingway」，要產生 Jeopardy 題目。

  • 寫到「The Sun Also Rises」時，主要參考文件 2（提到這本 1926 年的處女作）
  • 寫到「A Farewell to Arms」時，主要參考文件 1

在這個任務上 RAG-Token 表現較好，因為題目要整合多份文件的資訊。

RAG 流程總覽

Index（索引）：開發時或文件更新時做

預處理如影片先轉錄
→

→

Query（查詢）：每次提問時做

改寫問題可選
→

→
重排序可選
→

→
生成LLM 作答

換 embedding 策略，要把所有 chunk 重新索引。

怎麼找？語意搜尋與關鍵字搜尋

embedding（語意）BM25（關鍵字）
怎麼比向量相似度（如 cosine）詞彙比對，建立在 TF-IDF 上
擅長意思相近但用字不同精確字串、技術名詞、代碼

例：查「Error code TS-999」，embedding 可能只找到一般的錯誤碼說明，BM25 能比對到確切的字串。

做法：兩邊各找一次，再合併去重（rank fusion）。Anthropic 的測試中，兩者合用優於單用 embedding。

論文也發現：FEVER 這類以實體為主的任務，BM25 反而最好。

為什麼要切塊？

  • 放得進去：每個 embedding 模型有 context window，超過的部分會被截掉
  • 搜得到：chunk 要自己有意義，沒有脈絡的句子可能搜不到

經驗法則（Pinecone）：一段文字在沒有周圍脈絡時，人看得懂，模型通常也看得懂。

切太小有些問題答不了
切太大雜訊多，重點被稀釋

就算模型 context 很長也還是要切：大 chunk 增加延遲與成本，還有 lost-in-the-middle 問題（埋在長文中間的資訊會被漏掉）。

有哪些切法？

方法做法
固定長度決定每塊幾個 token。Pinecone 建議多數情況先從這裡開始
句子／段落用標點、換行或 NLTK、spaCy 切
遞迴字元依序嘗試用段落、換行、空白切
依文件結構PDF、HTML、Markdown、LaTeX 依標題與結構切
語意切塊相鄰句子語意差距大的地方切（實驗性）
加脈絡（LLM）替每塊補一段說明，下一頁詳述

怎麼找最佳大小？用代表性資料，試一個範圍（如 128/256 抓細節，512/1024 留脈絡），跑一批查詢比品質。也可以檢索後再把相鄰 chunk 一起取回（chunk expansion）。

進階：替每個 chunk 補脈絡

問題：切塊後，單看一塊會不知道它在講誰、哪段時間。

原本的 chunk「The company's revenue grew by 3% over the previous quarter.」
哪家公司？哪一季？不知道。
Contextual Retrieval（Anthropic，2024）「This chunk is from an SEC filing on ACME corp's performance in Q2 2023; …」＋原句
  • 由 LLM 根據整份文件與該 chunk 產生說明，通常 50–100 tokens
  • 說明在 embedding 與建 BM25 索引之前加上
  • 用 prompt caching 讓整份文件只載入一次；文章估算一次性成本約 1.02 美元／每百萬文件 token

效果有多少？再加一步重排序

top-20 檢索失敗率（越低越好）：

一般 embedding5.7%
＋Contextual Embeddings3.7%（降 35%）
＋Contextual BM252.9%（降 49%）
＋Reranking1.9%（降 67%）

Reranking：先取前 150 個，連同問題交給重排序模型打分，留下前 20 個給 LLM。代價是多一步延遲與成本。

這是 Anthropic 自家測試的結果（程式碼、小說、論文等資料），不保證在你的資料上相同；文章也強調要自己跑評估。

RAG 的另外三個優點（論文實驗）

1. 知識可以換：測 82 位換過人的世界領導人（索引替換，不重新訓練）

2016 索引、問 201670%
2018 索引、問 201868%
2018 索引、問 201612%
2016 索引、問 20184%

2. 更符合事實：人工比較 452 組 Jeopardy 題，RAG 較符合事實的比例 42.7%，BART 只有 7.1%。

3. 答案不在文件裡也有機會：在 NQ 上仍有 11.8% 答對（純抽取式模型為 0%）。

RAG 和微調差在哪？

RAG微調
補什麼知識行為（語氣、格式）
資料新鮮度更新文件即得新答案凍結於訓練時
更新成本低，重新索引每次需新訓練與評估
引用來源可以無
延遲多一步檢索不增加

口訣：缺知識用 RAG，缺行為用微調。兩者可併用：微調管語氣，RAG 管事實。微調也不能阻止幻覺。

比較表來自 Progress 的部落格，該公司販售 RAG 服務，結論偏向 RAG；Barnett 等人的論文也持類似看法，但指出最佳策略仍在研究。

RAG 的七個失敗點

#名稱白話在哪一段
1Missing Content資料裡根本沒有答案，還被問出一個回答索引內容
2Missed Top Ranked答案在，但排名不夠前沒被回傳檢索、重排
3Not in Context找到了，整併時被丟掉整併
4Not Extracted答案在 context 裡，模型沒抽對（雜訊、矛盾）生成
5Wrong Format要表格或清單，模型不照做生成
6Incorrect Specificity答案太籠統或太細生成、提問
7Incomplete沒錯，但漏了 context 裡有的資訊生成

來自 Barnett 等人（2024）的三個案例：研究、教育（AI Tutor）、生醫（BioASQ）。

做 RAG 的工程經驗

  • 只有運作中才能驗證：輸入在執行時才知道，需要持續監控與校準
  • 要調的東西很多：chunk 大小、embedding、切法、檢索、整併、context 大小、prompt
  • 加 metadata：在檢索內容附上檔名、chunk 編號，有助檢索與抽取
  • context 大一點較好：AI Tutor 中 8K 優於 4K
  • 別忘了安全：微調可能逆轉安全訓練，要測越獄

限制：外部知識來源（如 Wikipedia）也不會完全正確；論文還觀察到「檢索崩潰」——某些任務檢索器每次都取同樣的文件，生成器就忽略它們。

知識庫小於 200,000 tokens（約 500 頁）時，也可以整份放進 prompt，不用 RAG。

小結與自我測驗

  • RAG = 先檢索外部資料，再讓模型根據它回答
  • 流程：切塊 → embedding → 索引；提問時檢索 → 重排 → 生成
  • 切塊與脈絡決定檢索品質；語意與關鍵字搜尋可以互補
  • 缺知識用 RAG，缺行為用微調
  • 失敗點很多，只有實際運作才看得出來
Q1：模型答錯最新的人事資訊，該先考慮 RAG 還是微調？RAG。這是缺知識的問題，更新文件並重新索引即可。
Q2：RAG 回答說找不到相關內容，但文件裡其實有。可能是哪些失敗點？FP2（排名不夠前）或 FP3（整併時被丟掉）；也可能是 chunk 缺脈絡，可考慮 Contextual Retrieval 或 reranking。
Q3：使用者搜尋「Error code TS-999」，為什麼只用 embedding 可能不夠？embedding 偏語意，可能找到一般錯誤碼說明；BM25 可以比對確切字串，兩者合用較好。
