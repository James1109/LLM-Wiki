## 核心
- 一句話：**模型缺知識用 RAG；模型缺行為用微調**
- RAG 三步：檢索（retrieve）相關段落 → 擴充（augment）prompt → 生成（generate）有依據的回答；模型本身不改變，更新文件後下一個答案就反映
- 微調：用精選的輸入輸出範例（JSONL 對話）繼續訓練，改變權重；擅長語氣、輸出格式、領域用語、house style；不擅長當知識庫，事實不一定被可靠記住；知識凍結在訓練當時

## 比較表（原文）
| 面向 | RAG | 微調 |
|---|---|---|
| 資料新鮮度 | 更新文件即得新答案 | 凍結於訓練時，需重訓 |
| 更新成本 | 低，重新索引 | 每次更新需新訓練與評估 |
| 引用 | 可引用來源段落 | 無來源 |
| 幻覺風險 | 較低（以檢索文字為依據） | 對訓練集以外的事實不變或更糟 |
| 工程工作 | 索引流程、檢索調校、prompt 組裝 | 資料整理、訓練、評估、版本管理 |
| 資料量 | 用現有文件 | 通常 50–100 個以上精選範例 |
| 延遲 | 多一步檢索 | 不增加 |

## 併用與場景
- 可併用：微調負責語氣與格式，RAG 負責事實；RAG 與模型無關，生成端可用微調過的模型
- RAG 的典型場景：對即時產品文件的客服、財報等需附來源的問題、政策與合規查詢
- 微調仍有用的場景：輸出本身即是產品（嚴格 JSON schema 的分類器、品牌口吻）
- FAQ：微調不能阻止幻覺（會用完美的品牌口吻講錯事實）；RAG 通常較便宜，尤其長期
